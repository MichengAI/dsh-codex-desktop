# 桌面启动器架构基线

更新时间：2026-10-20 21:39（Asia/Shanghai）

本页是架构约束的唯一文档事实源；[交接摘要](../00-交接入口/05-技术架构基线.md)只保留入口。文末提及的本地历史归档不随仓库交付，不作为理解或验收本基线的必要依赖。

启动进度约束：百分比仅表示可计量的当前步骤（校验字节、解压条目、依赖文件），不得以计时模拟整个启动百分比；安装计数来自 pnpm，服务和页面启动保持不确定状态。初始化进程以 IPC 转发计量，错误页停止动画与计时。历史验收记录位于本地 I006「启动实际进度」归档。

## 架构目标

桌面层仅负责 Windows x64、macOS arm64/x64 与 Linux x64/arm64 的分发、运行时、子进程、窗口和生命周期；DSH 继续提供 Web UI、Agent、会话和业务能力。

## 运行链路

`Electron 主进程 → 内置 Node 运行时 → DSH 生产入口 → 127.0.0.1 随机端口 → BrowserWindow`

## 版本与实现事实源

- 随包 DSH 版本、启动 peer、社区插件清单及 overrides 以 [src/bundled-plugins.ts](../../src/bundled-plugins.ts) 的 `OFFICIAL_DSH_VERSION`、`OFFICIAL_LAUNCH_PEERS`、`BUNDLED_PLUGINS` 和配置函数为准，不在文档维护第二份版本表。
- Node 校验值、工具链及随包版本元数据以 [package.json](../../package.json) 的 `config`、`engines`、`packageManager` 为准；如打包流程通过 `build.extraMetadata` 注入元数据，还需核对最终制品的 `package.json`，不得用开发元数据替代制品事实。
- 预装构建见 [scripts/prepare-runtime.ts](../../scripts/prepare-runtime.ts)，安装和 bundle 边界见 [src/plugin-seed.ts](../../src/plugin-seed.ts)，更新分流见 [src/profile-updates.ts](../../src/profile-updates.ts)。

## 运行闭包

- Node 使用官方固定补丁版本，并按 Windows x64、macOS arm64/x64、Linux x64/arm64 校验 SHA256，具体值读取上述元数据。
- DSH 运行时从清单指定版本的 npm 包 `@deepseek-ai/dsh` 在打包时预装到 `runtime-dsh.tgz`，首启原子解压到安装目录下的 `dsh-runtime`；真实写入探测失败时回退用户数据目录。
- DSH 构建与启动器工具链以各自包声明和预装脚本为准；依赖安装由随包 pnpm 执行，不另抄容易过期的版本号。
- 官方运行时可随包装一份只读预装树，运行和在线更新写到安装目录旁的可写 `dsh-runtime`；社区插件在线更新写入 `~/.dsh/profiles/web`。Electron 缓存仍在 `%APPDATA%\\DSH Codex Desktop`，卸载时删除，且不得删除 `~/.dsh`。
- 运行时文件保留真实文件布局，不将 DSH 依赖临时解压到 ASAR 外。

## 启动与导航

1. Electron 获取单实例锁并展示本地启动页。
2. 以 `dsh web --port 0 --no-open` 启动 DSH；桌面窗口承载界面，禁止官方 Web 再打开系统浏览器。
3. 缓冲标准输出，识别 `dsh web:` 就绪行。
4. 仅接受 `http:`、`127.0.0.1` 与合法端口的 URL。
5. HTTP 健康检查成功后才加载 BrowserWindow。
6. 失败、超时或异常退出时显示中文错误和脱敏日志位置。

## 安全与生命周期

- Desktop bridge 使用用户数据目录中的私有包，经本次启动 `--patch` overlay 加载前后端，不再永久安装或登记到共享 Web profile。Desktop 服务声明同时校验启动标识、父子 IPC 和 pnpm 入口；独立 Web 使用自身安装通道。旧配置定向迁移且保留原文备份，历史记录位于本地 I006「桌面桥接动态注入」归档。
- 旧 bridge 迁移在插件补装前执行：移除共享 profile 的依赖、bundles 和 patch 声明，再删除旧包目录。即使已迁移配置仍检查残留文件；文件占用只警告并在下次启动重试。包目录链接只解除链接，不删除目标；整个 node_modules 为链接时跳过文件清理。清理逻辑已随 v1.0.49 发布，这是旧 bridge 的特定迁移边界，不授权按官方 scope 或未声明依赖批量清包；历史记录位于本地 I006「旧桥接残留清理」归档。

- Electron 使用 `nodeIntegration: false`、`contextIsolation: true`。
- 禁止任意 Electron IPC 暴露给 DSH 页面。
- 拒绝 `file:`、`javascript:`、`data:` 及非 loopback 导航；外部链接交给系统浏览器。
- 正常关闭通过 Node 引导脚本和父子进程控制通道触发 DSH 既有关闭逻辑。
- 超时只处理启动器创建的 PID；不得全局结束 `node.exe`。
- 不删除 `%USERPROFILE%\.dsh`，日志不得记录敏感数据。
- 卸载只结束 `DSH Codex Desktop.exe` 及其子进程，必须排除 `Uninstall*`，不得按安装目录无差别杀进程；完成后删除 `%APPDATA%\\DSH Codex Desktop` 与托盘 `NotifyIconSettings` 残留。
- Linux 窗口关闭即退出；CI 冒烟检查仅为 GitHub Runner 的未安装目录传递 `--no-sandbox`，发布应用保持默认沙箱策略。
- 桌面更新使用 GitHub Releases 元数据，默认启动完成后检查并提醒；设置可选择自动下载或仅手动检查，安装与重启必须明确确认。插件更新走 DSH 设置及插件市场，二者不得混用。Windows 解压版只检查并引导下载对应 zip，不得拉起 exe 安装器。

## 插件恢复模式

- 插件安装照常执行，安装错误单独记录并继续尝试加载 DSH，不将 pnpm 非零退出直接视为 DSH 启动失败。
- 只有实际 DSH 加载失败并有插件关联证据时，主进程才切换到当前窗口内的独立 `WebContentsView` 恢复页。无插件线索的系统或运行时错误展示普通启动错误。
- 客户端失败报告携带可选布尔字段 `workbenchReady`：官方布局内有可见会话输入框时为 true，主进程保留工作台，只记录错误，不确认完全健康或清理试恢复备份；旧报告不携带该字段时沿用失败处理。30 秒加载超时视为加载失败，存在近期插件变更时允许进入恢复，候选仅列相关变更项。
- 可疑项优先来自加载错误和前端报告；传递依赖错误映射到启用的所属插件；无具体错误来源时，最近健康配置后的插件变更仅作为候选线索。不得因非随包版本而批量归责插件。
- 用户确认后原子备份 profile 清单，仅隔离候选插件并保留其文件和依赖声明；无关插件继续加载。随包社区插件也可被诊断，官方核心运行时与桌面 bridge 不作为可卸载插件。
- 恢复页使用独立 sandbox preload，主进程只接受查询、确认恢复、保持隔离、单项恢复并重启、卸载隔离项、打开启动日志和返回工作台等受限 IPC。
- 卸载仅可处理恢复状态登记的隔离插件；插件名称与磁盘目标必须位于当前 profile 的 `node_modules` 中，禁止路径穿越。
- 恢复模式中的安装仍可激活无关新插件，对齐仅排除当前隔离项。试恢复失败仅重新隔离被错误指向的插件；无法定位时保留本次试恢复项作为候选。完整客户端健康前不清理恢复备份。
- 历史验证位于本地 I006「插件安装与恢复边界」归档；上述约束不依赖归档才能执行。


## 社区插件随包与在线安装

- 清单中的社区插件与市场组件在 `prepare-runtime` 写入 `runtime-plugins/store.tgz`，打包成单个压缩包，避免安装器解压上万个小文件。
- 打包前在空 Profile 中使用随包 Node/pnpm、store 和 cache 对全部内置固定版本执行真实离线安装及版本核验；失败阻止打包，联网安装不能替代该验证。首次启动用离线 store 把社区插件补种到 `~/.dsh/profiles/web`。
- 已装 `@michengai/dsh-codex-suite` 时按当前清单拆成独立功能插件；dshmarket 单独补种；每次启动按发布目录检查实际安装版本：缺失或低于内置版本时通过 pnpm 安装配套版本及其依赖，同版和更高版本保留。旧用户优先使用随包资源：先验证 v11 索引结构并取得写锁，再增量导入缺失文件（临时文件加同卷硬链接，不覆盖已有文件），以事务合并 SQLite 索引并保留原索引，安装元数据指向随包 cache；离线准备或安装失败均保留联网兜底；未知仓库位置使用 pnpm 默认仓库，不能静默切换到随包 store。不自动解除隔离或修改用户 patch。旧 pending 中低于发布基线的内置插件目标提升到基线，避免启动后再次降级。
- 社区包不得进入桌面官方运行时 `node_modules`。loader 的运行时锚点优先仅约束入口与 bundle 的解析顺序，不代表插件自己的 import 都共享同一份依赖；不同依赖树仍可能产生多实例，不能据此断言所有插件依赖单例安全或类身份安全。
- 随包 `resources/node` 同时提供 `node` 与 `pnpm`；DSH 子进程 PATH 前置该目录，code-ui 与 dshmarket 的 CLI 安装路径才能工作。
- 补种与在线兜底均失败时写 plugin-seed.log，并显示更新未完成及重试建议；用户确认后继续尝试启动现有 DSH。

## 官方运行时预装

- `prepare-runtime` 把 `@deepseek-ai/dsh` 和启动必需 peer 预装后打成 `runtime-dsh.tgz`，首启再解到安装目录。
- 桌面管理的官方 DSH 家族按清单版本统一锁定，并通过 `pnpm.overrides` 钉死 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*`，避免 `^` 范围把子包装到一半。
- 首启原子解压到选定的 `dsh-runtime`；安装目录不可写时整套运行时与插件仓库回退用户数据目录。启动时的随包基线对齐和既有 pending 落地不等于授权自动追随线上最新版本，更不授权清理用户 profile 包。
- 桌面运行时组件的安装与整组更新写入 `dsh-runtime`，不由桌面端补种到 Web profile。这不是「所有官方包都不得存在于 profile」：用户自行安装的独立官方 bundle、依赖声明及启用配置保留，不得因 `@deepseek-ai/` scope 批量迁移或删除。
- 官方运行时更新由桌面端按整组目标修改 `dsh-runtime`，手动更新的 pending 与随包基线对齐分别处理；启动期不得据此扫描清除 profile 中的官方 scope 或未声明包。
- profile 使用 hoisted 依赖布局，`node_modules` 顶层但未列于直接 dependencies 的包可能是 pnpm 链接的传递依赖。禁止按 scope、未声明或看似重复而手工删除；正常依赖增删与树重建交给 pnpm。定向处理无效 bundle 登记不等于删除包文件，也不授权清理无关声明。
- 安装包会变大，换来的是新用户首启不再解析、下载、链接整棵官方依赖。


## 原生侧栏材质（工作区实现，未发布）

Windows build 22621 及以上主窗口采用 Mica，主 WebContentsView 与标题栏透明；独立设置、关于、快捷键窗口不变。受限 preload 仅注入 data-dsh-native-backdrop=mica 能力标记，不开放窗口控制 API。旧系统和其他平台保留实色，新 UI 在没有标记时也保留实色。

两端构建、自动化与独立原生预览通过，未覆盖用户安装资源。正式 Desktop 全壳及第三方玻璃组合仍待验证。跨仓库验收由 UI I005 承接，历史记录位于相邻 UI 仓库本地 I005「原生材质验收」归档，不随本仓库交付。
